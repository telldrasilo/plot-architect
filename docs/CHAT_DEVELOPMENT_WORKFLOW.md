# Graphite — стандарт разработки в чате ChatGPT

**Статус: действующий процесс для обычной разработки.** Актуальный источник — GitHub `telldrasilo/plot-architect`, ветка `main`. Этот документ определяет **как разрабатывать код**, а не как публиковать Site или использовать пользовательские проекты.

## 1. Разделение сред

| Среда | Назначение | Что не подразумевается |
| --- | --- | --- |
| **Рабочая среда текущего чата ChatGPT** | Временная копия исходников, локальные изменения, запуск доступных проверок, подготовка PR | Не является ПК владельца, production или постоянным хранилищем |
| **GitHub `main`** | Единый источник кода и истории: ветки, PR, review, CI, merge | Merge не перезапускает никакой сервер |
| **Graphite Local на ПК владельца** | Рабочий редактор для просмотра/проверки принятого кода: Node.js, локальный SQLite, существующий Secure MCP Tunnel и приватный плагин «Graphite Local» | Это не среда выполнения команд ChatGPT и не автоматически синхронизируемая копия GitHub |
| **Опубликованные Site / production D1 / hosted MCP / плагины** | Отдельная, защищённая область, меняемая только с явного разрешения владельца | Не затрагиваются обычными PR и локальной синхронизацией |

**Work не используется для обычной разработки Graphite**, исправления UI, работы с GitHub, тестов или обновления локального Graphite. Не передавать в Work восстановление, перенос или анализ старых/пользовательских сюжетов. Устаревшие handoff-документы Site не являются инструкцией к обычной разработке.

## 2. Основной цикл — внутри текущего чата

1. **Задача и границы.** Прочитать `AGENTS.md`, нужные исходники и только релевантные документы. Для UX — актуальные решения в Library `/Планировщик сюжета/Development/UX_DESIGN_STANDARD.md`. Новейшее решение владельца важнее старого описания. Не исследовать прошлые релизы без причины.
2. **Синхронизация источника.** Получить актуальный SHA `main` и исходники через доступный GitHub-доступ; проверить, что рабочая копия соответствует выбранному SHA. Работать в **изолированном файловом окружении чата**, не на ПК владельца и не в директории с реальной SQLite. Создать отдельную ветку от актуального `main`.
3. **Изменения и локальная обратная связь.** Править связанные файлы вместе, запускать тесты и исправлять проблемы в рабочей копии **до** отправки коммитов. Не использовать GitHub Contents API как основной построчный редактор, если доступна полноценная рабочая копия. Не создавать PR на каждую промежуточную попытку исправления.
4. **Проверка по риску.** Выполнить подходящие тесты, проверку синтаксиса и сборку в доступной среде. Для изменений геометрии и взаимодействия — релевантные синтетические браузерные сценарии; для API/сохранения — контрактные и транзакционные тесты с временными данными. Если зависимости/Chromium недоступны, **честно отметить «не выполнено локально»**, не подменять тест осмотром кода.
5. **GitHub review.** Отправить узкую ветку, открыть PR к `main`, проверить diff (только ожидаемые файлы, без секретов, сюжетов, SQLite, сессий и артефактов), дождаться **обязательных применимых CI**, устранить обнаруженные ошибки в той же ветке и повторить проверки. Merge только после успешных проверок. PR и CI — единственный журнал разработки.
6. **При нескольких этапах.** Каждый PR проходит весь цикл `ветка → изменения → проверки → PR/CI → merge` **последовательно**. Следующий этап начинается от нового `main`; нельзя считать CI предыдущего этапа проверкой последующего.
7. **Результат.** Указать PR, SHA merge, реальные статусы проверок и то, что осталось непроверенным. **Не утверждать, что Graphite Local обновлён**, пока владелец не синхронизировал и не перезапустил его.

Обычные команды из каталога `site/` (выбор зависит от изменений и доступных зависимостей):

```bash
npm ci
npm run check
npm run check:v2
npm run test:local
npm run build
```

Для изменённого UI запускать целевые тесты `qa/browser/` при наличии установленного Playwright/Chromium. Не выполнять тесты против реальных проектов или постоянного `graphite-dev.sqlite`.

## 3. Если у среды чата нет прямого Git/сети или тестовых зависимостей

Проверить ограничения **до** обещаний о полноценной локальной проверке.

- При недоступном `git clone` использовать подключённый GitHub для чтения зафиксированного состояния `main` и переноса необходимых исходников в файловую рабочую область чата, насколько это возможно. Для небольших документов/исправлений допустима запись ветки штатными GitHub-инструментами.
- Если невозможно собрать **полную согласованную** рабочую копию, не объявлять, что локально выполнены полный build или все тесты. Проверить то, что действительно доступно; CI может дать независимую проверку отправленного изменения.
- Если риск изменения требует локального интеграционного/браузерного теста, который нельзя провести и который не покрыт CI, **остановиться перед merge** и сообщить конкретный пробел. Не обходить защиту PR, не изменять тесты ради зелёного статуса и не подменять проверку запуском Work.
- Отсутствие прямого доступа к пользовательскому ПК не является основанием запрашивать секреты, доступ к SQLite или публичный порт.

**Приоритет — файловая разработка в чате. GitHub API-редактирование — резервный транспорт, а не новый основной метод.**

## 4. Синхронизация с рабочим Graphite Local на ПК

**Это отдельный шаг после merge, не автоматическое действие GitHub и не часть среды ChatGPT.** Рабочий локальный сервер читает файлы в `D:\Graphite\plot-architect`. Пока их не обновили и не перезапустили Node.js, пользователь видит предыдущую версию.

1. В браузерном Graphite завершить сохранение, дождаться окончания MCP-запросов.
2. На ПК владельца остановить работающий Node/tunnel через `Ctrl+C` (не во время записи). Проверить чистоту Git-дерева, перейти на `main`, выполнить `git pull --ff-only`. **Не** делать `reset --hard`, force-pull или удаление пользовательских файлов.
3. Если изменились зависимости — отдельно выполнить `npm.cmd ci` из `site/`. Запустить существующий `npm.cmd run dev:node-tunnel` в сохранённом PowerShell с уже настроенным окружением; новый терминал требует безопасно восстановить runtime-переменные по существующей инструкции.
4. Проверить `http://127.0.0.1:8788/` и, если нужно, чтением `list_projects` через уже подключённый «Graphite Local». Для проверки новой UX-функции использовать **синтетический** проект либо явно разрешённый владельцем сценарий. Не изменять реальные сюжеты ради smoke-test.

**Полная инструкция запуска и безопасного повторного входа:** [NODE_LOCAL_DEVELOPMENT.md](NODE_LOCAL_DEVELOPMENT.md). ChatGPT помогает подготовить команды, но **не утверждает, что выполнил их на ПК**, если у него нет подтверждённого доступа и результатов. Подключённый MCP-плагин — интерфейс Graphite и его данных, **не** механизм автоматического `git pull` или удалённого управления Windows.

## 5. Неизменные границы

- **GitHub merge не означает deploy** и не даёт разрешения менять Site, production D1, hosted MCP, конфигурацию туннеля или Plugin Skill.
- Не загружать в GitHub секреты, содержимое пользовательской SQLite, реальные сюжеты, browser-cookie, токены, логи с ключами.
- Сохранить локальный loopback `127.0.0.1:8788`; не публиковать порт или заменять действующий Secure MCP Tunnel обходным подключением.
- Изменения графовой модели, серверного контракта, авторизации или хранилища требуют отдельных тестов и явного согласования соответствующих защищённых действий.
- Если отдельно разрешён **hosted release**, применяется [RELEASE_POLICY.md](RELEASE_POLICY.md); этот документ не даёт такого разрешения. Старинные Work/Sites handoff-файлы не возобновляют публикацию автоматически.

## Короткая формула

**ChatGPT (временные файлы + доступные локальные тесты) → GitHub (PR + CI + merge) → владелец синхронизирует GitHub `main` на ПК → перезапуск Graphite Local → проверка результата.**

Без Work как обязательного этапа и без скрытого изменения рабочего хранилища.

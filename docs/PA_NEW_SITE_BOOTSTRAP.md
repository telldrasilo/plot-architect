# Plot Architect — новая приватная установка Sites

**Назначение:** однократная установка с нуля, отдельно от старого Site. Этот документ — критерии выпуска, а не инструкция по миграции.

## Подготовлено в GitHub

- Исходник: `telldrasilo/plot-architect`, `site/`, проверенный commit `main` (для первого выпуска фиксировать конкретный SHA).
- `site/.openai/hosting.json`: `{"d1":"DB","r2":null}` **без** `project_id`. Новый ID назначает Sites.
- `site/wrangler.sites.jsonc`: только локальная конфигурация, `database_id=00000000-0000-0000-0000-000000000001` никогда не использовать как размещённую D1.
- Существующая `drizzle/0001_initial.sql` и журнал миграций, REST, Sites-native auth, MCP, UI и JS-контракты должны остаться неизменными при первом создании.
- Node/REST/MCP/security, Vite, Chromium и bootstrap CI проходят на синтетических данных. CI не доказывает реальную авторизацию владельца и deployment.

## Только штатные действия Sites

1. В **новой** задаче Work открыть совместимый исходный проект по зафиксированному SHA, проверить соответствие `site/` конфигурации и создать **новый приватный Site**. Не открывать старый Site для переноса исходников и не извлекать из него D1.
2. Создать **новую собственную D1** с именем binding `DB`. Проверить, что используются миграции проекта для новой пустой БД, без предупреждений об удалении/замене чужой базы. Никакого ручного Wrangler deploy, кастомной авторизации или подмены базы.
3. Проверить private preview и конфигурацию. Выполнить **Save version**, затем **Deploy version** только при отсутствии конкретных рисков и в пределах разрешённого создания нового приватного Site. Зафиксировать Site ID, версию, deployment ID и URL.
4. Проверить закрытый доступ, /api/health, REST сохранение и перезагрузку; при первом входе UI может автоматически создать пустую «Новую историю». Тестовые записи — только на **новом** Site. MCP /mcp должен объявить семь инструментов: `list_projects`, `create_project`, `get_project`, `get_context`, `get_changes`, `preview_patch`, `apply_patch`.
5. **Обязательная проверка поддержки обновлений:** заново открыть Site через штатное Edit в Sites, убедиться, что возвращён актуальный checkout без ошибки `Unable to prepare the Site`. Затем применить **только заранее проверенное безопасное изменение** из последующего GitHub-коммита (например, заголовок вкладки), выполнить второй Save version → Deploy version. Если исходники не открываются или данные/связи неожиданно меняются — **STOP**, не считать Site готовой заменой.
6. Плагин нового Site создавать/подключать **отдельным штатным действием** после успешного выпуска и без подмены старого плагина; проверка семи live инструментов через плагин — отдельный результат, не путать с MCP discovery самого Site.

## Границы

- Старый Site, его версия, D1, плагины и сюжеты не трогать и не переносить.
- Не создавать пользователей, новые секреты или сервисы в обход Sites. Не включать генерацию P5/P6: в UX-014 пока только сохранение и отмена задания.
- Сбой native checkout, ошибка D1/авторизации или реальное предупреждение о замене данных означает остановку, а не нештатную публикацию.
- Источник кода — GitHub. Любые будущие изменения: ветка → PR → применимый CI → merge; native Sites Save/Deploy отдельно.

## Факты для приёмки

Записать **фактически подтверждённые** Site ID, URL, saved version, deployment, owner-only, D1 binding, миграции, семь MCP, создание пустого проекта и UX-014. Отдельно указать результат **холодного повторного открытия исходников** и **второго выпуска**. Непроверенное не маркировать PASS.

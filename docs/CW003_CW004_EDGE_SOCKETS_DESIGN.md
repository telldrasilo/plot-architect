# CW-003 / CW-004 — стрелки мышью и индивидуальные гнёзда Graphite

**Статус:** проектная спецификация на рассмотрении, **не реализация** и не разрешение на публикацию.  
**Основание:** принятое намерение владельца CW-003 (drag-to-connect) и CW-004 (отдельное гнездо каждой связи), исследование `GRAPHITE_CREATIVE_WORKFLOW_RESEARCH.md`, UX-стандарт `/Планировщик сюжета/Development/UX_DESIGN_STANDARD.md`.  
**Код-ориентир:** `telldrasilo/plot-architect`, `main` @ `c4a6ca75fa41414ec4c6817876bee7376bc3d3cd` (05.11.2026).

## 1. Обязательное намерение и предложенные уточнения

**Уже принято владельцем:** создавать направленные связи перетаскиванием между карточками; каждое существующее подключение обладает отдельным различимым входным или выходным гнездом, без фиксированного лимита количества.

**Предлагаю как рабочий дизайн (требует проверки UX):**
- При наведении/фокусе на сюжетную карточку показывается свободное **выходное** гнездо «Начать связь». Остальные принадлежащие связям гнёзда становятся заметнее. Карточка сама по себе продолжает перетаскиваться.
- Автор тянет из свободного выходного гнезда; до отпускания рисуется **только временная стрелка**. При приближении к допустимой целевой карточке у неё появляется отдельное свободное входное гнездо — предварительная точка **именно новой связи**.
- Отпустил на допустимой цели → создаётся связь с направлением «из источника к цели», по умолчанию типа `precedes` («Следом»), и отдельная пара постоянных гнёзд этой стрелки. Тип изменяется компактно рядом со стрелкой, не обязательно через полный инспектор.
- Перетаскивание уже существующего **конечного** гнезда → предпросмотр новой цели. Исходная связь не удаляется и не изменяется до успешного сохранения.
- Esc, `pointercancel`, пустой холст, неверная цель или ошибка сохранения → отмена без частичной записи.
- Двухкликовый способ / клавиатурное «Связать» остаётся доступной альтернативой; **мышиный жест — основной**.

**Не входит пока:** автоматическое создание причинности по геометрии, точная ручная фиксация мест гнёзд, смешанные сюжетно-редакторские стрелки, связи сюжетных узлов с смысловыми полями и редакторскими заметками, полная миграция графовой модели.

## 3. Модель идентичности гнёзд

**Не добавлять новые сущности `sockets` в JSON проекта.** Хранится сама связь с существующим ID, `from`, `to`, `type` и при необходимости `workspaceId/draftRelation`.

Вычисляемые UI-идентификаторы:
- `{edgeId}:source` — выходное гнездо конкретной стрелки;
- `{edgeId}:target` — входное гнездо той же стрелки;
- `new:{nodeId}:source` — временная ручка для нового соединения, не хранится;
- `candidate:{gestureId}:target` — временное гнездо у кандидата, не хранится.

ID стабильны при изменении координат и размеров нод, перемещении камеры, zoom и перерисовке. Переподключение существующей стрелки **сохраняет `edgeId`**, изменяя только допустимый конечный `nodeId`; тип связи по умолчанию не меняется.

Логическая принадлежность: `{edgeId, endpointRole, nodeId, scope}`, где `scope=plot` или ID одной рабочей области. Нельзя спутать гнездо внутренней черновой связи с сюжетным.

## 4. Чистый геометрический модуль (первый PR)

Предлагаемый модуль `site/src/edge_socket_geometry.mjs`, без DOM, данных проектов, серверных запросов или побочных эффектов.

Вход `layoutEdgeSockets({nodes,edges,bounds,mode})`:
- `nodes`: видимые ноды выбранного **одного слоя** с мировыми координатами;
- `edges`: активные связи того же слоя с ID и концами;
- `bounds[nodeId]`: фактическая `{x,y,width,height}` карточки в **мировых** координатах (текст адаптивной высоты измеряется на DOM, но в этот модуль DOM не передаётся);
- `mode`: `full` либо режим недоступных интерактивных портов.

Выход:
```js
{
  ports: Map<edgeIdAndRole, {
    edgeId, role, nodeId, scope, side, x, y, rail, ordinal
  }>,
  byNode: Map<nodeId, {incoming: Port[], outgoing: Port[]}>,
  warnings: [] // визуальная плотность/коллизии, не отказ в хранении
}
```

**Правила размещения первой версии:**
1. При `full` исходящие гнёзда — вдоль правой стороны, входящие — вдоль левой. Это сохраняет сложившееся в Graphite направление слева направо. Стрелки «назад» допустимы и по-прежнему получают предупреждение о направлении, но тип отношения не меняется.
2. Для каждого `nodeId + role` отсортировать гнёзда по `centerY` противоположной карточки, затем по ID связи (детерминированный tie-breaker). Внутри одного активного жеста размещение существующих гнёзд **заморожено**; пересортировка только после отпускания и успешного обновления данных.
3. Для одного гнезда позиция по высоте — центр. Для нескольких — симметричное распределение вокруг центра с ориентиром расстояния **20 мировых px**, расстояние может увеличиваться до 30px при достаточном месте. Защитный отступ от верха/низа карточки ~16px.
4. Когда на высоте карточки не хватает места, **не** ограничивать число стрелок и **не** сокращать расстояние до неразличимости. Продолжать тот же упорядоченный ряд на внешней вертикальной **рейке гнёзд**, выступающей выше/ниже карточки. Рейка принадлежит карточке и не меняет её размер, содержимое или координаты. Перекрытия с соседями — отдельная задача раскладки / адаптивной визуализации; обнаруженные коллизии отражать в диагностике, а не удалять порты.
5. Гнездо для новой стрелки — отдельная временная точка **свободного места**, которую располагают вне уже занятых точек; при подтверждении новая связь входит в пересчитанную систему и получает собственный ключ.
6. Геометрия не записывается в БД. При перечитывании проекта порт восстанавливается по `edgeId`, а его мировые координаты пересчитываются.

**Обязательно:** при текстовых карточках использовать реальную высоту DOM (`offsetHeight` или `getBoundingClientRect/scale`), а не `105`, `56` или половину заданной высоты. При обычном zoom не переставлять порты в мировых координатах.

**Маршрутизация:** `connector`, `smartConnector` и прямые линии черновиков получают пару уже рассчитанных якорей `source/target`; функция построения пути **не выбирает порт**. Путь, маркер и отдельный hit-target должны точно кончаться в соответствующих координатах. На compact/map сохраняются текущие обзорные якоря и агрегация; постоянные гнёзда не должны изображать ложные отдельные события на карте.

## 5. Отрисовка и слои

- Общая логика геометрии, **два адаптера**: активный сюжетный SVG и SVG рабочей области. Временный drag-путь — отдельная overlay-графика, чтобы `renderEdges` не разрушал захваченный DOM-элемент.
- Размер видимой точки ~6px радиуса в полном масштабе; реальная интерактивная зона не менее ~20–24 **экранных** px и рассчитывается с учётом `pan.scale`. Сохранять просвет между соседними зонами либо применять выбор ближайшего гнезда по координате.
- Видимость: постоянные гнёзда приглушены, становятся заметны при наведении/выделении карточки или конкретной связи. Во время соединения целевая нода показывает **новое** свободное гнездо. На дальнем зуме гнёзда не интерактивны.
- Для доступности: кнопка-альтернатива «Связать», различимый клавиатурный фокус и подписи `aria-label`, недопустимые цели обозначены не только цветом. На мобильных/сенсорных устройствах в первой версии остаётся альтернативный способ соединения; точное touch-поведение — отдельный этап.
- Не рисовать постоянные кнопки поверх каждой ноды и не вводить глобальный режим «Редактирование стрелок».
- Гнёзда не могут поглощать обычный drag за тело карточки; события начинаются **только** на специальной ручке. Точки и линии не должны блокировать инспектор, меню и текстовые поля.

## 6. Машина состояний жеста CW-003

```text
idle
  └─ pointerdown на выходной ручке → armed
       ├─ click без порогового движения → (доступный двухкликовый fallback)
       └─ перемещение > 5 screen px → dragging
            ├─ допустимая нода под курсором → valid_target
            ├─ пустота / запрещённая цель → dragging (без цели)
            ├─ Esc / pointercancel / потеря окна → cancelled → idle
            └─ pointerup на допустимой цели → pending_save
                 ├─ подтверждённая запись и readback → committed → idle
                 └─ ошибка / конфликт → original_unchanged + retry/cancel
```

Hit-test при `setPointerCapture`: использовать `document.elementsFromPoint` либо сравнение реальных прямоугольников нод с положением курсора; нельзя полагаться только на `pointerenter` целевой карточки. Координаты курсора переводятся через уже существующий `pointerToWorld`. Привязка к целевой ноде допускается по её **карточке целиком**, а не только попаданием точно в маленькую окружность.

Проверить допустимость цели **перед** рисованием положительной подсветки: другая нода, та же область данных, незамороженный источник/цель; сюжет/черновик/поле/заметка не смешиваются; скрытая оригинальная нода замещения не выбирается. Новый сюжетный тип по умолчанию `precedes`, но позиция на холсте сама по себе не подразумевает `causes`. Сохранять текущую политику запрета дублированной пары `from→to` для канона до отдельного решения о параллельных типизированных связях.

## 7. Переподключение стрелки — отдельная машина состояний

**Нынешний недостаток:** `editor.js` удаляет старую стрелку в обработчике `reconnect` до выбора новой цели. Это действие должно быть заменено **атомарным** сохранением после выбора.

- На hover/выделении связи конечное гнездо становится ручкой «Перенести конец».
- Во время drag исходная связь сохраняется в графе и в БД. На полотне показывается временный маршрут с новым кандидатом и возможность Esc.
- По отпусканию проверить существование исходной связи, допустимую цель, отсутствие дубликата, актуальную ревизию.
- На успехе обновить `to` того же `edgeId` **один раз**, сохранить историю Undo и прочитать подтверждённое состояние. При любой ошибке старая связь остаётся неизменной.
- Старую команду `Переподключить` в инспекторе на этапе выпуска привязать к тому же безопасному механизму, а не поддерживать две реализации. До выпуска нового механизма ничего не менять.
- `gapLinks` (редакторские контекстные ссылки заметок) не превращать в сюжетные стрелки и не переподключать через этот механизм.

## 8. Транзакции и граница сохранения

**Сюжет → сюжет:** модель `edges` уже содержит `id/from/to/type`, миграция не требуется. Предлагается единый клиентский `commitCanonicalEdgeEdit`: предварительно дождаться ожидающих записей, построить новую копию графа, провести существующий защищённый `PUT` с `expectedRevision`, подтвердить повторным чтением, только после этого считать жест завершённым. При сетевой неопределённости сначала readback и проверка ревизии/наличия `edgeId`, не отправлять несколько случайных созданий. Удалять старую связь заранее нельзя.

**Черновик ↔ черновик одной рабочей области:** обычный `PUT` закономерно блокирует защищённые draft-рёбра. Требуется **предлагаемое**, пока не реализованное расширение внутреннего локального workflow: `add_draft_edge` / `reconnect_draft_edge`, или один тип команды с явной операцией. Минимальный контракт будущего шага:
```json
{
  "kind": "add_draft_edge",
  "workspaceId": "w1",
  "edge": {
    "id": "draft-edge-id",
    "from": "draft-a",
    "to": "draft-b",
    "type": "precedes",
    "draftRelation": "internal"
  },
  "expectedPreview": {
    "workspaceId": "w1",
    "from": "draft-a",
    "to": "draft-b",
    "eligible": true
  }
}
```
Это **пример для проектирования**, не зарегистрированный сейчас API. Реальный `expectedPreview` должен фиксировать точные затронутые ID/содержание, тип, текущую принадлежность и ожидаемую ревизию. Применение — за одну транзакцию/receipt с защищённым CAS и идемпотентным `operationId`; повтор не должен дублировать ребро.

**Не смешивать:** черновик разных областей; черновик с каноническим событием; черновик с защищённым оригиналом; редакторскую `gapLink` с сюжетной `edge`. Такие жесты показывают недопустимую цель и ничего не записывают. Существующее поведение `boundary-proposal` и внешних стрелок замещения остаётся отдельным рассмотрением.

Пока проектный контракт не утверждён, **не менять MCP route/schema, Site, опубликованную D1, плагин и реальные сюжеты**. Если реализация без этого невозможна, работа останавливается до отдельного решения.

## 9. Предлагаемая последовательность маленьких PR

1. **PR-A: только чистый геометрический модуль + его unit-тесты**. Никаких новых стрелок, кнопок, операций или изменений данных. Проверить детерминированность, отдельные якоря и адаптивные размеры.
2. **PR-B: только отображение существующих индивидуальных гнёзд** в сюжетных и черновых SVG с сохранением smart/direct route, обзорного масштаба, zoom/pan и старых кликов. Нет новых записей.
3. **PR-C: drag-to-create для канонических событий**, отдельный оверлей, hit-test, управление типом, подтверждённое сохранение. Старая команда «Связать» остаётся.
4. **PR-D: защищённое переподключение канонических стрелок** без delete-before-select. Один Undo, конфликт и сетевые сбои безопасны.
5. **PR-E: операции черновых связей** в локальном защищённом workflow, затем жест создания/переподключения во временной рабочей области. Доказать, что принятие в сюжет не меняет оставшиеся черновые связи.
6. **PR-F: плотные наборы и полировка UX**: расширяемые рейки, route-кроссинги, жесты touch/клавиатуры, оптимизация сотен/тысяч связей. Не скрывать крайние случаи с ложным лимитом.

Разделение A/B допускает сначала проверить и отрегулировать геометрию без опасной записи. Каждая кодовая часть — ветка → PR → применимые тесты и CI → merge. Дальнейшее обновление единого UX-стандарта — после решения владельца по предлагаемым уточнениям, не отдельный дублирующий журнал.

## 10. План обязательных тестов

**Unit (чистая геометрия):**
- одна связь; 2, 3, 5, 20 и 100 входов к одной ноде; несколько выходов; неравномерная высота карточек;
- порядок `edges` во входном JSON не меняет итоговый порядок/координаты портов; ID после reload неизменны;
- zoom/pan не меняет мировые координаты портов, а hit-зона сохраняет экранный размер;
- длинные карточки и ресайз, отрицательные/большие мировые координаты;
- рейка для перенасыщения не накладывает порты друг на друга, не изменяет размер/положение карточки;
- source/target одного ребра различимы; обратная стрелка и два противоположных ребра имеют уникальные гнёзда;
- `compact/map`: интерактивных портов нет, связи и обзорные мосты остаются читаемыми.

**Chromium (синтетические графы):**
- создание мышью: hover → drag → целевое гнездо → drop; создана одна связь и две собственные точки;
- body drag не создаёт связь; Esc, `pointercancel`, пустой холст, self-link и cross-scope не меняют данные;
- выделение, zoom/pan, движение/resize карточек, скрытые ноды и overlay взаимодействия;
- перемещение конца сохраняет старую связь до успешного подтверждения; ошибка и устаревшая ревизия сохраняют старый `edgeId` и конец;
- альтернативное соединение по кликам/клавиатуре не сломано;
- draft↔draft одна область — одна защищённая операция; draft↔plot и draft↔другая область отклоняются;
- после reload соединения и логическая уникальность гнёзд восстановлены, внешний вид предсказуем;
- плотный граф UX-015: не создавать тысячи интерактивных DOM-ручек в обзорном масштабе, не разрушать адаптивные мосты.

**Транзакционные тесты:** серверная CAS-ревизия, receipt replay, запрет повторного `operationId` с другим payload, отсутствие записей при preview/cancel, сохранность оригиналов переработки, отсутствие generic PUT для protected draft, readback после принятия.

Только фикстуры и синтетические БД — без доступа к реальным сюжетам.

## 11. Критерии готовности и оставшиеся продуктовые решения

### Считаем CW-004 готовым, если
- `N` входящих и `M` исходящих связей дают `N+M` различных **логических** гнёзд и соответствующие им якоря;
- в одной позиции не оказываются две активные точки одной стороны; перенос/ресайз не меняет ID;
- канон, черновики и обзор используют одну геометрию там, где это возможно, без потери старых связей;
- карточки остаются читаемыми, число связей не ограничивается UX-фиксированным максимумом.

### Считаем CW-003 готовым, если
- от выходного гнезда к целевой карточке можно создать связь одним жестом;
- тип «Следом» не навязывает причинность, при необходимости тип доступен в контексте стрелки;
- отмена/ошибка оставляют граф неизменным, сохранение подтверждается сервером;
- прежний способ соединения доступен, созданные стрелки сохраняются после reload.

### Требуют проверки макетом, прежде чем считать окончательно утверждёнными
1. Расстояние 20–30 world px между портами, размер точки и размер hit-цели.
2. Постоянная приглушённая видимость портов vs только hover/selection; правило для плотных узлов.
3. Стоит ли в первой версии разрешать перетаскивать только **конец** стрелки или оба её конца.
4. В каком порядке показывать значения типа связи после успешного создания: автоматически «Следом» + компактная кнопка, либо небольшое меню на drop.

**Важно:** эти параметры — предложения проектирования; CW-003/004 фиксируют принцип, но не конкретные числа и рисунок.
